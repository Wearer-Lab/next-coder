      Common service path

      All supported control surfaces preserve device authentication, account/environment ownership, policy, idempotency and compact results. The cloud routes commands; the paired local connector reaches private T3; T3 owns the coding agent. Media capabilities must be advertised by the actual firmware build.

      Evidence, boundaries and open questions

      This is an explanatory model of checked-in firmware, not an emulator executing C++ and not a pixel-perfect screenshot archive.

      Observed on physical Hosyond

      Firmware 0.2.17: Verify T3 → local confirmation → gateway → connector → T3 → HOSYOND_PRODUCTION_E2E_OK visible on the device.

      Firmware 0.2.18: a real microphone recording → local Parakeet → T3 → “voice test successful” visible, confirmed by the owner on October 23. Approximately 43 seconds from gateway receipt to reply on that attempt; this is not a latency guarantee.

      Code / test evidence

      Source snapshot 359bfdd. The functional release gate passed 1,469 tests; all 15 firmware environments compiled. Source branches cover duplicate gestures, stale confirmations, uncertain receipts, upload replay and reply polling. Builds and native tests do not establish physical touch, radio, audio, OTA or loss recovery.

      Console-owned today

      Sign-in and claiming; connect-machine enrollment; saved-action creation and layout assignment; device profiles/grants; transcript editing/review; provider approvals and agent user-input responses. The console may support more than Hosyond’s current input surface.

      No on-device keyboard, arbitrary prompt composer, message edit/delete, full transcript browsing, camera capture or spoken reply playback is established by this flow.

      Open verification

      Repeated confirmation stress, Wi-Fi/router outages, sleep/wake, long-running voice soak, physical OTA rollback/power cuts and complete cross-board hardware qualification remain separate checks. Other boards must not inherit Hosyond’s physical proof.

      The current English Parakeet checkpoint is not multilingual. Other users receive their own connector-local setup and account-scoped routing; their computer must be online.

      Questions this map exposes

      • Should rejection have an undo/review step? Current gateway REJECT is immediate; APPROVE has a second dialog.
      • Should failed uploaded voice jobs offer a clear device-side recovery action? Current workflow often hands off to the console.
      • How discoverable are the header drawer, Home thread swipe, and the difference between OPEN, TALK and ACTIONS?
      • Does the user understand gateway hold versus agent permission versus agent question?
      • What should users see during laptop wake-up and long local speech startup?
      • When a retained recording outlives navigation, is its frozen destination clear enough?
